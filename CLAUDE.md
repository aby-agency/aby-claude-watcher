# Aby Claude Watcher

Electron desktop app monitoring Claude Code sessions in real-time.

## Dev

```bash
npm install
npm start        # production
npm run dev      # with devtools
npm run build    # DMG — REQUIERT Node ≥ 20.19 (cf. .nvmrc: 22)
```

> **Node ≥ 20.19 obligatoire pour `npm install`/`npm run build`.** Depuis Electron
> 41.8+, son downloader `@electron/get` est passé en ESM pur : le postinstall
> `require()` casse (`ERR_REQUIRE_ESM`) sur Node < 20.19. `nvm use` lit le `.nvmrc`
> (Node 22). Le champ `engines` du package.json documente la contrainte.

## Architecture

- `main.js` — Electron main process, window, IPC, tray
- `watcher.js` — Session discovery (`~/.claude/sessions/`), JSONL parsing, state machine
- `socket.js` — Unix socket IPC for `cc`/`cwa` wrappers
- `focus.js` — Terminal focus (AppleScript iTerm2/Terminal/Warp), resume, launch
- `config.js` — Persistence (debounced writes, saveSync on shutdown)
- `preload.js` — Context bridge (contextIsolation: true)
- `island.js` + `island-model.js` — Dynamic island ancrée à l'encoche (fenêtre transparente + logique pure testée)
- `ui/` — Renderer (vanilla HTML/CSS/JS, no framework)

## States

| State | Color | Trigger |
|-------|-------|---------|
| thinking | purple `#a78bfa` | Last event = `user` text (Claude processing) |
| running | blue `#3b82f6` | Last event = `assistant` with `stop_reason: "tool_use"` |
| waiting | green `#22c55e` | `status: idle`/`shell` de session.json (CLI ≥ 2.1.260) ; sinon `end_turn` + 2s no activity. Si des tâches de fond sont encore ouvertes (`status: shell` ou JSONL) : chip cyan « N bg process » + notifs mutées, l'état reste waiting |
| delegating (« Délégation ») | cyan `#06b6d4` | `waiting` alors que des sous-agents / un workflow / une tâche Bash de fond reconnue (pas un serveur) travaillent encore, ou que le CLI se dit `busy` — état de PRÉSENTATION calculé par main.js, ne notifie pas |
| pending | amber `#f59e0b` | `status: waiting` (sauf `waitingFor: dialog open`) ; hook `PermissionRequest` pour l'instantanéité |
| error | red `#ef4444` | `isApiErrorMessage` event OR silent crash after explicit resume |
| completed | (purged) | Session file gone + PID dead → removed from UI |

## Key decisions

- **Présence CLI (v2.13.0) — `status` de `~/.claude/sessions/<pid>.json` est l'AUTORITÉ sur l'état gros grain.** Depuis ~2.1.260 le CLI réécrit ce fichier à chaque rendu : `status` = `busy` (tour en cours OU délégués actifs — agents locaux/distants, teammates in-process, workflows, monitors) | `idle` | `shell` (idle + Bash de fond ouvert) | `waiting` (dialogue bloquant, `waitingFor` = « permission prompt » par défaut, « input needed », « sandbox request », « worker request », « goal proposal », « dialog open » = menu local) ; `statusUpdatedAt` date la transition. Module pur `presence.js` (`readPresence` + `presenceDecision`, tableau de décision testé `test/presence.test.js`), appliqué par `applyPresence` à chaque `scan()`. Règles : `at = statusUpdatedAt` (jamais Date.now()) ; présence antérieure au démarrage → transition SILENCIEUSE (restaure le pending sans `pendingMarks`, conservé en fallback CLI ancien) ; garde d'ordre = une présence plus vieille qu'un pending posé par le hook ne le dégrade pas ; « dialog open » ne passe JAMAIS en pending (chip vert « Dialogue ouvert », choix Paul) ; `end_turn` JSONL ignoré tant que le CLI dit `busy` (délégation en arrière-plan, défaut depuis CLI 2.1.232) ; notif « Inactif » mutée sous `shell`/dialogue/`busy` avec bannière tardive au retour `idle` (`presenceMuted`). `delegatingNow` compte aussi `presence.status === 'busy'` (couvre les teammates in-process et agents distants invisibles dans `subagents/`). CLI sans `status` valide → comportement historique intact. `scan()` masque aussi les workers `spare` et le jumeau `parkedJobId` d'une session passée en arrière-plan (comme `claude agents`), et `kind` ≠ `interactive` vaut headless. Vérifié dans le binaire 2.1.263 (fonctions `QVe`/`sOo`, enum `["busy","shell","idle","waiting"]`). Au REDÉMARRAGE, `fastInitialLoad` rejoue le tail AVANT `applyPresence` (ordre voulu : la présence prime) : un `end_turn` restauré passe donc `waiting` puis la présence `busy` le mute et `delegatingNow` l'affiche « Délégation » — libellé cyan au lieu de bleu, notif muette dans les deux cas, assumé (ruling 2026-09-07). Dans les deux branches de `scan()` (découverte et trackée), `applyPresence` est appelé APRÈS `watchJsonl` ; quand le JSONL n'existe pas encore, `watchJsonl` diffère `startFileWatch` de 3 s et ce rejeu peut écraser transitoirement l'état présence — auto-réparé au scan suivant (2 s). Garde symétrique : tant que le CLI dit `waiting`, les events JSONL ne dégradent pas l'état (log `event JSONL … ignoré (presence waiting)`) ; garde d'ordre logguée une fois par `statusUpdatedAt` (`[presence] … ignoré (antérieur au pending)`).
- JSONL `tool_use` events only written AFTER user approves permission — cannot detect permission prompts (from the JSONL alone — the `PermissionRequest` hook is the signal, see below)
- **Détection « en attente » = hook GLOBAL (v2.4.0), signal `PermissionRequest` (v2.12.0).** Le pending (permission prompt) n'est visible que via un hook Claude Code qui ping le socket. **Le hook installé est `PermissionRequest` (+ `Notification`), PLUS `PreToolUse`.** PreToolUse part pour CHAQUE outil — auto-approuvé, en bypass, et pour les outils des SOUS-AGENTS (même `session_id`, seul `agent_id` les distingue, cf. docs hooks) — et l'event `tool_use` n'atterrit dans le JSONL que 1 à 12 s après le ping (médiane 3 s mesurée sur main.log), donc le défèrement 1 s ne filtrait rien : 128 « Action requise » fantômes sur une seule session bypass (a7e2ea88, 2026-08-28), et un parent bloqué sur un fan-out d'agents restait ambre tant qu'aucun agent n'était `running` frais (< 30 s) — c'est le « action requise sur des trucs où y'a pas d'action requise » d'Etienne (2026-09-02, capture : « Action requise · 4 min » sous 15 lignes d'audits). `PermissionRequest` (CLI ≥ 2.0.45) ne part QUE devant un vrai prompt : jamais en bypass, jamais pour un outil auto-approuvé, et un prompt levé par un sous-agent bloque bien l'utilisateur → compté. `Notification` est routée par `notification_type` (forwardé par le hook, whitelist `[a-z_]`) : `permission_prompt`/`elicitation_*_dialog`/`agent_needs_input` → pending, `idle_prompt` → correction waiting, tout le reste (`auth_success`, `agent_completed`, `quota_*`…) ignoré ; sans type (CLI ancien) → comportement historique. `markPending` ignore désormais tout `PreToolUse` (un `settings.local.json` per-projet posé par un vieux `cc` peut encore en envoyer) ; l'ex-garde `bypassPermissions` est retirée (morte : `PermissionRequest` ne part pas en bypass, et `session.permissionMode` n'était de toute façon plus lu — CC ≥ 2.1.x le pose sur les events `user`, pas en event `permission-mode`). `install-hooks.js` : `LEGACY_EVENTS = ['PreToolUse']` → nos blocs y sont retirés à la migration (`dropLegacyBlocks`, hooks tiers intacts, clé supprimée si vide), `removeHookFromFile` les couvre aussi. L'app installe ce hook dans `~/.claude/settings.json` (le SEUL fichier user-scope qui charge les hooks — `settings.local.json` user-scope est ignoré, cf. [[reference_claude_hooks_scope]]) → marche pour TOUTES les sessions, tout projet, SANS le wrapper `cc`. `install-hooks.js` : `installGlobalHook`/`removeGlobalHook` (merge non destructif, self-heal du chemin, testé `test/install-hooks.test.js`) ; toggle `permissionHookEnabled` (défaut on) ; `applyPermissionHook()` au démarrage + à chaque toggle. **PIÈGE asarUnpack** : le script hook DOIT être un vrai fichier exécutable — packé dans `app.asar` il n'est PAS accessible au shell (le hook ne fire jamais, pending jamais détecté pour les users de l'app installée — bug historique constaté par Etienne). D'où `asarUnpack: ["bin/**"]` dans le build + `getDefaultHookPath()` qui remappe `app.asar` → `app.asar.unpacked`. Avant v2.4.0 : hook installé UNIQUEMENT par `cc` en per-projet (pointant sur l'asar cassé) → seul un dev avec un hook global manuel vers son checkout voyait le pending.
- **Le pending est ANCRÉ sur disque (`config.pendingMarks`).** Corollaire du point précédent : le pending est le seul état invisible dans le JSONL (rien n'y est écrit tant que l'utilisateur n'a pas répondu), donc purement RAM. Sans ancrage, tout redémarrage de l'app le reconstruisait depuis le dernier `assistant` en `stop_reason: tool_use` → **running**, et comme `PreToolUse` ne re-fire JAMAIS, la session restait bleue jusqu'à ce que l'utilisateur réponde de lui-même (constaté en live sur TrainBox le 2026-07-25 : question à 18:45:57, app relancée à 18:50:29, session affichée « en exécution » ensuite). `setState` écrit/purge la trace `{mtimeMs, tool, at}` à l'entrée/sortie du pending ; `fastInitialLoad` appelle `restorePending()` AVANT d'appliquer l'état déduit, et la trace prime tant que le **mtime du JSONL est inchangé** — mtime plus récent = la question a été traitée app éteinte → purge. Le mtime est le seul signal fiable ici, PAS un seuil de délai (un pending légitime peut durer des heures). Restauration en `isInitial=true` → badge ambre restauré, pas de notif rétroactive (règle établie). Branche idempotente si l'état restauré depuis `config.sessions` était déjà pending : `setState` serait un no-op muet, on émet `session-updated` à la main sinon les tokens/model relus ne remontent pas. Traces orphelines purgées dans la passe `knownIds` de `start()` et par `deleteSession`.
- Only `end_turn` reliably signals "waiting for user" — no stale timer (caused false positives)
- **État `delegating` — un tour fini pendant que les délégués travaillent n'est pas de l'inactivité.** Même faux positif que `job`, autre cause : la session a lancé des sous-agents (ou un workflow) puis rendu la main ; ils la réveilleront. Elle s'affichait « Inactif » en vert SOUS les lignes des agents encore en cours, bannière needs-you comprise. C'est un état de **présentation** (`STATES.DELEGATING`, jamais produit par la state machine) : le watcher ne voit pas les sous-agents, ils vivent dans `<session>/subagents/` et sont lus par main.js — `delegatingNow()` + `hasLiveDelegation()` (pur, testé). Substitué à `waiting` dans `effectiveStateName` ET `serializeSession` (qui réutilise les scans déjà faits), + garde de silence sur `session-waiting`. Volontairement PLUS LARGE que `hasBlockingForegroundAgent` : celui-là cherche ce qui BLOQUE (foreground `running` frais) pour corriger un pending ; ici on cherche ce qui TRAVAILLE, donc agents détachés et runs de workflow comptent aussi. Les agents `stale` comptent également (silence 30 s–5 min = un agent qui lit un gros diff, cf. `ERROR_TIMEOUT_MS`) : les exclure ferait clignoter le libellé entre « Délégation » et « Inactif » pendant que les lignes d'agents restent affichées sur la carte. Libellés : « Délégation » / « Delegating », cyan « ça tourne sans toi » (décision Paul — le mot fait la différence). Depuis v2.8.0 c'est le SEUL état cyan (l'ex-état `job` est devenu le chip « N bg process »).
- **Vocabulaire « background » (v2.5.0, révisé v2.8.0)** : la section des sessions headless s'appelle **« Headless (n) »** (ex-« Background (n) ») — « Headless » = les sessions sans terminal, « N tâche(s) » = les tâches Bash backgroundées (chip cyan, ex-« N bg process » puis brièvement « en fond » le 2026-09-07 — Paul voulait court, puis le chiffre toujours visible ; en anglais « N task(s) »). L'ex-badge d'état « Background » (`job`) a été supprimé en v2.8.0. Le chip porte un anneau qui tourne (`.bg-spin`, même arc CSS que le badge d'état — pas de SVG) et l'île le reprend en sous-ligne cyan `.subrow-bg` sous la session (champ `bgTaskCount` sur la rangée de `buildIsland`, testé) ; seul ce chip tourne, « Dialogue ouvert » et « Chrome » restent statiques (ce n'est pas du travail). **Serveur vs tâche (même jour)** : deux « en fond » se ressemblaient alors que l'un servait un site et l'autre attendait un build. `bg-task.js` (pur, testé) : `classifyBgCommand(command)` → `'server'` sur une liste de motifs « ça tourne sans fin » (`npm run dev|start|serve|watch`, `vite|next|electron|nodemon…`, `uvicorn|flask run|rails s`, `docker compose up`, `tail -f`, `ngrok`, `--watch|--reload`…) testés segment par segment après retrait des `cd …` (« dev » dans un chemin ne compte pas ; `electron-builder` n'est pas `electron` — `(?![\w-])` et non `\b`), sinon `'task'` ; `bgTaskOpening(event)` lit le `tool_use_id` du tool_result et `timedOutAfterMs` (absent = backgroundée exprès, présent = parquée après timeout → `deliberate:false`). Le watcher garde `session.recentBash` (Map tool_use_id → {description, command}, fenêtre `RECENT_BASH_MAX` 30, remplie par `captureBashCalls` dans processAssistantEvent ET le tail de fastInitialLoad, jamais persistée) et `session.bgTaskInfo` (Map id → fiche), en PARALLÈLE du Set `bgTasks` (inchangé, les tests le forgent en `new Set([...])`) ; `bgTaskDetails(session)` sort les fiches pour `serializeSession.bgTasks`, une tâche sans fiche = `'task'` anonyme. Rendu : chip `.server-chip` « N serveur(s) » GRIS ARDOISE (#94a3b8) avec glyphe `>_` STATIQUE (un serveur tourne, il ne bosse pas) + chip « N tâche(s) » CYAN (famille « Délégation ») avec spinner, chiffre toujours affiché, les deux possibles sur une carte, sur une LIGNE DÉDIÉE sous la ligne d'état (`bgLineHTML` → `.compact-card-bg` / `.card-bg-line`, icône activité `ICONS.process`, même gabarit que branche/session) — sur la ligne d'état ils débordaient dès deux chips (« 1 tâche » seul sur une 2e ligne, capture Paul 2026-09-07) ; « Dialogue ouvert » et « Chrome » restent sur la ligne d'état, ils qualifient l'état ; `title` = description — commande (tronquée 90) — « depuis HH:MM » — « parquée après timeout ». Île : `bgGroups(list, count)` (pur, testé) → une sous-ligne par famille, serveur d'abord (`.subrow-server` gris + `.subrow-term`) puis tâches (`.subrow-bg` cyan + `.subrow-spin`), `title` = descriptions jointes. **Reconstruction à l'attachement = passe DÉDIÉE `rebuildBgTasks`** (appelée par fastInitialLoad après son tail) sur tout le JSONL depuis la fin, plafond `BG_SCAN_MAX_BYTES` 64 Mo, préfiltre texte (`"name":"Bash"`, `"backgroundTaskId"`, `<task-notification>`) avant JSON.parse — 20 ms sur les 5,8 Mo de foundx. PIÈGE qui a motivé cette passe : le tail d'état s'arrête au premier `assistant` (64 Ko), et une ouverture 75 Ko avant la fin (gros tool_results) n'avait pas de fiche → foundx restait vert « Inactif » sur un `uv run … analyze` (Paul, 2026-09-07). `known` = tool_use retrouvé (commande connue) ; une ouverture dont le Bash est hors plafond reste anonyme → pas de « Délégation ». L'heuristique se trompe d'icône au pire, le tooltip reste la vérité.
- **PIÈGE hook non quoté (corrigé v2.5.0) — le pending ne marchait PAS sur l'app installée.** Claude Code exécute la commande d'un hook via `/bin/sh -c` : un chemin non quoté est découpé au premier espace. La commande installée pointait sur `/Applications/Aby Claude Watcher.app/…/aby-permission-hook.sh` → sh cherchait `/Applications/Aby`, le hook ne partait jamais, et le pending n'était jamais détecté (visible dans le terminal : `PreToolUse:Bash hook error … /Applications/Aby: No such file or directory`). **Invisible en dev**, où le checkout n'a pas d'espace dans son chemin — c'est la seconde moitié du bug d'Etienne, la première étant `asarUnpack`. `install-hooks.js` écrit désormais `shellQuote(hookPath)` (quotes simples : rien n'y est interprété, apostrophe interne échappée `'\''`) ; `isOurHook` dé-quote avant de comparer (`shellUnquote`, tolérant nu/simple/double) donc les entrées des versions ≤ 2.4.x sont RECONNUES et migrées en place par le self-heal, sans doublon. Corollaire : le hook per-projet de ce repo (`.claude/settings.local.json`) pointait encore sur `app.asar/bin/` (chemin d'archive, pré-v2.4.0) — retiré, le hook global le couvre.
- **Tâches de fond — chip « N tâche(s) » (ex-« N bg process »), PAS un état (v2.8.0, révise l'état `job` de v2.5.0).** Un tour qui se termine sur une tâche de fond encore ouverte (Bash `run_in_background`) reste ambigu : suspendu à un PROCESS qui va réveiller la session (réimport Godot 20+ min, TrainBox 2026-07-25 — la bannière à chaque fin de tour était le faux positif d'origine), OU tour réellement fini avec un process laissé tourner exprès (serveur dev, `electron --remote-debugging-port` — constaté 2026-07-27 : Claude avait conclu son TLDR, la carte affichait « Background » cyan et muet alors que la discussion attendait Paul). Un process long-vivant ne « complète » JAMAIS → l'état `job` mentait jusqu'au garde-fou 45 min. Arbitrage Paul : les deux vérités sont séparées — l'état de la CONVERSATION redevient `waiting` (« Inactif », vert, compté idle dans l'île), et les tâches ouvertes deviennent un **chip cyan « N bg process »** (`bgTaskCount` dans `serializeSession`, `bgChipHTML` cartes grid + compact). **Révisé 2026-09-07, une fois serveur et tâche distingués** (`bg-task.js`) : une TÂCHE de fond RECONNUE (fiche `known: true`, kind `task`) qui tourne encore après la fin du tour vaut « Délégation » (cyan, comptée « ça bosse » dans l'île), via `hasLiveBgTask(bgTaskDetails)` dans `delegatingNow` et l'override de `serializeSession` — elle réveillera la session, exactement comme un agent ; un SERVEUR laisse « Inactif » (la conversation est libre), et une tâche SANS fiche aussi (présence `shell` seule ou ouverture hors tail) : sans preuve on ne ressuscite pas le mensonge de `job`. Le compteur de durée n'est pas touché par cet override (règle générale des états de présentation) ; les notifs `session-waiting` restent MUTÉES tant qu'un bg est ouvert (le spam TrainBox reste réglé ; log `[notif] muet (bg process ouvert)` ; une permission `pending` notifie, elle — action requise, bg ou pas). Détection inchangée, ENTIÈREMENT dans le JSONL (le fichier `tasks/<id>.output` SURVIT à la fin, il ne dit rien de son vivant) : ouverture = event `user` avec `toolUseResult.backgroundTaskId` ; fermeture = `<task-notification>…<task-id>ID</task-id>…<status>…</status>` injectée deux fois (`queue-operation` via `event.content`, puis `user` via `message.content` string) — n'importe quel statut ferme (completed/failed/killed). `bgTaskOpened`/`bgTaskClosed` purs et exportés ; `session.bgTasks` (Set). Pièges toujours traités : (1) le rappel idle 60s du hook Notification est structurellement vrai pendant tout le bg → ignoré car la session est déjà `waiting` (`markPending`) ; (2) la reprise par task-notification est routée en RUNNING (`task-notification`) et non en THINKING/`user-prompt`, sinon `setState` remettrait à zéro le cooldown de notif sur une fausse frappe. Restauration SANS persistance : `fastInitialLoad` reconstruit `bgTasks` depuis le tail seul (la fenêtre est un suffixe : si l'ouverture y est, la fermeture éventuelle aussi → pas de chip fantôme ; ouverture hors fenêtre = tâche oubliée, dégradation gracieuse). Garde-fou `JOB_STALE_MS` (45 min sans event) dans `scan()` : un process tué à la main n'émet jamais sa notification — le chip resterait affiché et la session muette à vie ; à la purge, `maybeNotifyWaiting` émet la bannière tardive. Seuil large : un build DMG de 20-30 min n'écrit RIEN dans le JSONL et reste légitime ; corollaire assumé, un serveur dev vivant > 45 min sans activité de session perd son chip.
- **Durée d'état « Inactif · 12 min » (v2.9.0).** `session.stateSince` (epoch ms) posé par `setState` à chaque VRAIE transition (`stateChanged`) via un 5e param optionnel `at` (défaut `Date.now()`), persisté dans `config.sessions`, exposé par `serializeSession` — les overrides de présentation (delegating, running-sur-pending-bloqué) ne le touchent PAS : le libellé peut basculer « Inactif » ↔ « Délégation » sans reset du compteur. Restauration : le `stateSince` persisté survit si l'état recalculé est identique (no-op) ; sinon `at = mtime du JSONL` (la transition a eu lieu app éteinte), et `pendingMark.at` pour un pending restauré (plus précis). **JAMAIS de timestamp fabriqué** : jamais de « 0 min », null = pas d'affichage. **PIÈGE pré-seed (deux itérations pour l'attraper)** : (1) le no-op `initial-scan` ne posait rien → toute config pré-feature restait sans durée à vie (la session inactive depuis des heures ne re-transitionne plus) — d'où l'amorce dans le no-op de `setState`, gardée par `stateSince == null && typeof at === 'number'` (seuls les 2 appels de `fastInitialLoad` passent un `at` : l'amorce ne peut PAS fuiter en marche courante) ; (2) la branche de DÉCOUVERTE pré-seedait `Date.now()`, ce qui fermait cette amorce pour toute session jamais persistée (install neuve : « Inactif · 1 min » après 2 h) → pré-seed `null`, `fastInitialLoad` pose le mtime dans les deux cas. Surfaces : cartes grid + compact = span `.state-duration[data-since]` DANS le badge, rempli par le ticker 1 s existant (`updateDurations`, écrit seulement si la valeur change), typo compact alignée 10px/600/uppercase ; tooltip `title` = horodatage absolu (« depuis 14:32 », date au-delà de 24 h, clé `state_since_abs`) posé au render (un timestamp absolu ne périme pas) ; île = champ `minutes` réintroduit sur les rangées (`buildIsland(sessions, config, now)` — `now` injecté pour la pureté), rendu « · 12 min » dans `.r-state`, granularité minute au rythme des refreshs existants, pas de ticker seconde. Formatage dans `ui/state-duration.js` (module pur IIFE node/window, `formatMinutes`/`formatStateDuration`, testé). Vue micro exclue. À arbitrer un jour : l'île dit « En attente » où les cartes disent « Inactif » (`rowHtml` n'applique pas `state_waiting_idle`, divergence pré-existante rendue visible par la durée partagée).
- **Libellé de modèle — module pur `ui/model-label.js`.** L'ex-`formatModel` (enterré dans renderer.js, non testé) exigeait un numéro en DEUX parties (`^(opus|sonnet|haiku)-(\d+)-(\d+)`) : toute la génération 5 (`claude-opus-5`, `claude-sonnet-5`) et Fable (jamais dans l'alternance) retombaient sur le `return model` brut — la carte affichait « claude-opus-5 ». `formatModel` (IIFE, double export node/window, testé) gère les 4 familles, la version optionnelle en 1 ou 2 parties, les alias nus des sessions SDK (`opus` → « Opus ») et le suffixe de variante entre crochets (`claude-opus-5[1m]` → « Opus 5 »). **PIÈGE date-en-version** : le `(\d{1,2})(?!\d)` n'est pas cosmétique — sans le garde, `claude-opus-5-20260101` rendrait « Opus 5.20260101 » (c'est bien la date qui est ignorée dans `claude-haiku-4-5-20251001` → « Haiku 4.5 »). Un slug non reconnu est rendu TEL QUEL, jamais avalé : si le format de nom change encore, on voit un slug moche plutôt que rien. `null` = rien à afficher, et chaque surface décide : grid met « — » (grille de détails à cases fixes), la vue compacte OMET sa ligne. Surfaces : case `Modèle` en grid (inchangée) + nouvelle ligne `.compact-card-model` (« ✦ Opus 5 », sous l'UUID, même gabarit que branche/session en `--text-muted`). Micro et île exclues.
- **`<synthetic>` n'est pas un modèle (`isRealModel`, watcher.js).** Les events synthétisés par Claude Code (erreurs API) portent `model: "<synthetic>"` et étaient assignés tels quels : une session passée en erreur perdait DÉFINITIVEMENT son vrai modèle et affichait « <synthetic> » jusqu'à sa fin. Garde aux 2 points d'assignation (`fastInitialLoad` + `processAssistantEvent`) : tout pseudo-modèle entre chevrons est ignoré, le dernier modèle réel reste en place.
- Waiting delay: 5s (avoids false positives between rapid tool calls)
- Notifications: 30s cooldown per session to avoid spam
- Pending sound deferred 5s — rings only if still pending/waiting at fire time (permissions approved in seconds shouldn't ding); fire-time check calls `watcher.refreshSession()` first (polled state lags the real click by flush + 250ms poll — approval at the wire must not ring on stale state; residual race = CC flush latency only, irreducible); toast stays immediate; every emit/skip logged `[notif]`
- Notification hook 60s idle reminder ("waiting for your input") ≠ permission: hook forwards `idle` bool; already-waiting session → ignored (no re-ding, no amber flip); busy-looking session → corrected to waiting (`hook:idle-reminder`), not pending

- Config saves debounced 500ms, `saveSync` on shutdown
